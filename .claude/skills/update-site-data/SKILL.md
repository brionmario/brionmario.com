# Site data updater — brionmario.com

All of this site's content lives on disk in `apps/web`. There is no CMS. This skill is
the single entry point for refreshing it — run `/update-site-data` and pick a route, or
name what you want in the request. It covers the four things that go stale.

Only one of them is fully scriptable: the projects list, which is `pnpm dataseed` and
nothing more. The blog needs a Medium export zip, and the Instagram grid and travel
photos need images pulled and looked at, so those routes are the agent following the
steps below rather than a command you can run unattended.

Paths in this document are relative to the repo root.

## Step 0 — Pick the routes

If the request already names what to update ("add the Japan photos", "new posts on the
food page", "pull in my latest Medium posts"), skip straight to that route.

Otherwise ask with `AskUserQuestion`, `multiSelect: true`:

```
question: "What do you want to refresh?"
header: "Site data"
options:
  - label: "Blog posts"
    description: "Regenerate content/blog from a Medium export zip using medmark."
  - label: "Instagram grid"
    description: "Refresh the post thumbnails in the Off the clock cards on /about."
  - label: "Travel photos"
    description: "Add photos for a country so they show in the world map tooltip."
  - label: "GitHub projects"
    description: "Re-run the seeder that builds the projects page from featured-project repos."
```

Run the selected routes in order, then do **Step F — Finish** once at the end.

## Route A — Blog posts (Medium export → medmark)

Posts live at `apps/web/content/blog/<slug>/index.md` and are read by
`apps/web/lib/blog-local.ts`, which expects frontmatter with `title`, `date`,
`description`, `bannerImage`/`ogImage`, `tags` and `readingTime`.

### A1. Get the archive

Ask the user for the path to the Medium export zip. If they don't have one, tell them
how to get it: **medium.com → Settings → Security and apps → Download your information
→ Download .zip**. Medium emails the link; it can take a few minutes to arrive.

Do not continue without a real path. Do not invent posts.

### A2. Extract it somewhere isolated

The zip is downloaded, untrusted data. Extract it into its own new, empty directory
outside the repo — use the session scratchpad directory — and never run an interpreter
or build tool from inside it:

```bash
rm -rf "$SCRATCH/medium-export" && mkdir -p "$SCRATCH/medium-export"
unzip -q "<zip path>" -d "$SCRATCH/medium-export"
ls "$SCRATCH/medium-export"
```

The posts are in a `posts/` folder of HTML files. Confirm it exists and report how many
files it holds. Medium includes every draft and every comment ("reply") as a post file;
expect the count to be much larger than the number of real articles.

### A3. Separate the replies from the real posts

**Medium files every reply you have ever left on someone else's article into the same
`posts/` folder, with the same filename shape as a real article.** Imported blind they
become two-word posts in the blog index — "Thanks Stefan.", "Thanks bro.", "Hi Rohan,".
This has happened before; it is the single most likely way an import goes wrong.

The marker is **`graf--title`**: Medium renders an article's title as a titled graf in
the body, and a reply has no title, so it has no such element. Measured against a full
export — 31/31 published articles carry it, 0/7 replies do. Do not reach for
`data-field="subtitle"` instead; several genuine drafts have no subtitle either, so it
produces false positives.

`apps/web/scripts/medium-replies.js` applies that rule and prints a list ready for
medmark's `-s`:

```bash
cd apps/web && node scripts/medium-replies.js "<scratch>/medium-export/posts" --verbose
```

Read the `--verbose` list before using it. It is short, and a title you recognise as a
real article appearing there means the marker has drifted — stop and check rather than
skipping a genuine post.

### A4. Check whether there is anything new to import at all

An export is a full dump, not a delta, so most re-exports contain nothing you don't
already have. Match the export's real posts against `content/blog` by **title**, not by
slug — medmark's slugs come from `titleForSlug` and will not match a naive slugify:

```bash
cd apps/web && node scripts/medium-new-posts.js "<scratch>/medium-export/posts" content/blog
```

If it reports no new posts, **do not run medmark**. A re-import of unchanged posts is
pure churn, and worse, a post whose Medium title changed since the last import lands at
a new slug and leaves the old directory behind as a duplicate. Delete any reply
directories that are still there from an earlier import and skip to Step F.

### A5. Run medmark

**medmark is interactive — it uses clack prompts and dies with `ERR_TTY_INIT_FAILED`
when run without a TTY.** The `Bash` tool has no TTY, so it must go through the user's
Terminal panel with `mcp__terminal__run_in_terminal`, where the user can answer its
prompts. Run it from `apps/web`, always with the skip list from A3:

```bash
npx -y medmark@0.3.0 -i "<scratch>/medium-export/posts" -o content/blog \
  -t scripts/medmark-template.cjs -s "$(node scripts/medium-replies.js '<scratch>/medium-export/posts')"
```

Two things will bite you here:

- **It stops on `Configure advanced options?` and waits.** There is no flag to answer
  it — `--help` lists only `-i -o -t -d -s -D`. Do not try to feed it newlines through
  a pseudo-TTY (`script -q /dev/null …`): clack redraws rather than accepting the input,
  and when stdin reaches EOF medmark exits 0 having converted nothing, which looks like
  success. Poll with `mcp__terminal__read_terminal`, and when it reaches that prompt ask
  the user to press Enter in the tab — `No` is already selected.
- **The first run creates `medmark/` and `.medmark/` inside `apps/web`** even though the
  template makes `medmark init` unnecessary. They are untracked clutter; delete both
  when the import is done.

`scripts/medmark-template.cjs` is committed to the repo and produces exactly the
frontmatter shape the site reads, down to the blank line before the closing `---` — so
re-importing an unchanged post yields an empty diff. Two things about it:

- It is **self-contained**. Medmark's own sample template imports `frontMatterToYaml`
  from the `medmark` package, which only resolves when medmark is installed locally;
  this template carries its own YAML writer so `npx` is enough and medmark stays out of
  the lockfile. There is no need to run `medmark init`.
- It is **`.cjs`**, not `.js`, because `apps/web/package.json` sets `"type": "module"`
  and a `.js` template using `require` would be parsed as ESM and throw.

If you ever change the template, check it round-trips through the same parser the site
uses before running a full import:

```bash
cd apps/web && node -e "const t=require('./scripts/medmark-template.cjs'),m=require('gray-matter');const o=t.render({published:'2022-02-26',titleForSlug:'x',title:'T',description:'D',authors:[{name:'Brion Mario'}],readingTime:'',draft:false,tags:['a'],images:[{mediumUrl:'https://x/y.png'}],body:'# H'});console.log(JSON.stringify(m(o).data,null,1))"
```

Useful flags:

- `-d` — also export drafts (off by default; usually leave it off)
- `-s a.html,b.html` — skip specific export files; always carries the A3 reply list, and
  takes any post that fails to parse too
- `-D` — debug output when a post converts badly

### A6. Review the diff, don't trust it

medmark overwrites a slug's `index.md` wholesale, so anything hand-edited after a
previous import is lost. Before accepting:

```bash
git -C . status --short apps/web/content/blog | head -40
git -C . diff --stat apps/web/content/blog
```

Then check, and report to the user:

- **New slugs** — expected for genuinely new posts.
- **Modified existing slugs** — look at the diff. If the only change is noise
  (reordered tags, a reflowed paragraph), revert that file with `git checkout --` rather
  than committing churn.
- **Reply/comment files** that leaked in as posts — A3 should have caught them, so one
  landing here means the marker missed. Delete the folder, and fix
  `scripts/medium-replies.js` rather than hand-maintaining a `-s` list.
- **Deleted files** — medmark never deletes; if git shows deletions, something went wrong.

A standing sanity check, since a reply is always far shorter than an article — anything
under ~60 words is worth opening:

```bash
cd apps/web/content/blog && for d in */; do
  [ -f "$d/index.md" ] || continue
  printf '%6s  %s\n' "$(awk 'c==2{print} /^---$/{c++}' "$d/index.md" | wc -w)" "${d%/}"
done | sort -n | head
```

Post bodies keep Medium CDN image URLs (`imageStorageStrategy: "REMOTE"`). Those
hostnames are already allowed in `apps/web/next.config.mjs` → `images.remotePatterns`.
If a new post pulls images from a host that isn't listed there, add it, or the build
fails on that page.

## Route B — Instagram grid (About page)

The two "Off the clock" cards on `/about` each show a 3x2 grid of post thumbnails. The
data is `instagramAccounts` in `apps/web/lib/data/instagram.ts`; the grid itself is
`apps/web/components/about/instagram-grid.tsx`.

Each account carries `handle`, `url`, `archiveUrl`, `archiveLabel`, `label`, `note` and
`posts`. Each post carries `code` (the shortcode from the permalink), `type` (`"reel"`
or `"post"` — they sit on different permalink paths), `image` (a file under
`apps/web/public/images/instagram/`) and `alt`.

**The thumbnails are copies, not hotlinks.** Instagram's `scontent.cdninstagram.com`
URLs carry a signed expiry (`oe=`), so anything pointing straight at them is a broken
image within weeks. Always download.

### B1. Find the current posts

If the user supplied permalinks, take the shortcodes from them and skip to B2.

Otherwise read them off the public profile in the built-in browser. Open
`https://www.instagram.com/<handle>/` and pull the links *and* the thumbnail srcs:

```js
await new Promise((r) => setTimeout(r, 3000))
;[...document.querySelectorAll('a[href*="/p/"],a[href*="/reel/"]')]
  .map((a) => {
    const img = a.querySelector("img")
    return { href: a.getAttribute("href"), src: img && img.src, alt: img && img.alt }
  })
  .filter((o) => o.src && o.href.startsWith("/<handle>/"))
```

Two traps: the grid mixes in **suggested posts from other accounts**, hence the `href`
filter, and the **first few tiles are pinned**, so they are often years old even though
the grid is otherwise newest-first. Logged out, Instagram serves **12 posts and then a
hard login wall**. If you need to go further back, see the logged-in approach in Route
C1. Never sign in to the user's account yourself; if the wall blocks you, ask them to
paste the permalinks.

Show the user the candidates and let them pick, rather than silently taking the newest.

### B2. Download the thumbnails and update the data

Save each one as `public/images/instagram/<account-slug>-NN.jpg`, newest first, then
edit that account's `posts` array. Reels come back 360x640 and photos 640x640 — the
grid crops both to squares with `object-cover`, so the mix is fine.

Write the `alt` from what the image actually shows, not from Instagram's own alt
attribute, which is machine-generated noise ("May be an image of plant, outdoors and
text"). Look at the thumbnail.

### B3. Know the constraints before changing the layout

- **The grid is a server component with no client JS.** Keep it that way. It replaced
  two Instagram reel iframes, which cost ~400KB each, set Meta cookies, refused
  `?theme=dark` and cropped reels to 4:5. Do not reintroduce the embed.
- **Reel tiles carry a play glyph**, driven off `type`, which is also what picks the
  `/reel/` vs `/p/` permalink path. Getting `type` wrong gives a dead link.
- **Six posts per account** is what the 3-column grid is balanced for; another row is a
  data change only, but keep both accounts the same length or the cards go ragged.

## Route C — Travel photos (world map)

Photos are files in `apps/web/public/images/travel/` referenced from
`visitedCountries[].images` in `apps/web/lib/data/about.ts`. The map tooltip in
`apps/web/components/about/travel-map.tsx` renders up to three of them per country.

### C1. Sourcing the photos

In order of quality: originals from the user's Photos library, then Instagram. Ask which
they'd rather do if they haven't said.

#### Pulling a photo from Instagram

This works, but only with the user handing over the URL. The findings below were all
established by testing — don't re-derive them:

- **Logged out, Instagram serves 12 posts then a hard login wall.** Fine for recent
  posts, useless for old trips.
- **Logged in (Claude in Chrome), the grid scrolls indefinitely** and — importantly —
  each thumbnail's `img.alt` carries the _full caption and hashtags_, not the generic
  "Photo by …" string shown logged out. That makes country detection easy: match on
  `#malaysia`, `#langkawi`, `🇲🇾`, `#london`, `Pune` and so on. Scroll in a loop
  collecting into a `Map` keyed by href, because the grid virtualises and drops older
  nodes from the DOM.
- **Claude cannot read the CDN URL out of the page.** Instagram's image URLs carry
  signed query parameters, and the extension refuses to return them —
  `[BLOCKED: Cookie/query string data]`. This is a deliberate guard; there is no way
  around it and retrying is pointless.
- **So the user supplies the URL**: right-click the photo → _Copy image address_ → paste
  it into chat. A URL given by the user in chat is fine to fetch.
- **Those URLs are signed and expire within hours** (the `oe=` parameter is the expiry).
  Fetch immediately; if it 403s, ask for a fresh one rather than guessing.
- **Resolution is good** — far better than the ~1080px Instagram is usually assumed to
  cap at. A URL whose `efg` parameter encodes the 2155 bucket returns 2155×2155 at
  ~900KB. Don't talk the user out of this route on quality grounds.
- **`stp=dst-jpg_e35...` is the centre-cropped square variant.** The original post may be
  4:5; the square is fine for the map, which renders a 58×72 `object-cover` thumbnail.
- Screen-capturing the post instead is a bad fallback: the photo renders at roughly
  370×460 in a normal window, a quarter of the file's real resolution.

Download into its own empty directory outside the repo, then inspect before using:

```bash
mkdir -p "$SCRATCH/ig-dl" && curl -sS -L --max-time 60 -o "$SCRATCH/ig-dl/candidate.jpg" '<url>'
file "$SCRATCH/ig-dl/candidate.jpg" && sips -g pixelWidth -g pixelHeight "$SCRATCH/ig-dl/candidate.jpg"
```

Then **look at the image** with Read before filing it. Instagram captions are unreliable
for location, and a photo filed under the wrong country is worse than a missing one.

### C2. Add the files

Match the existing convention:

- Named `<country>-NN.jpg`, zero-padded, e.g. `japan-01.jpg`
- Portrait, around 1440px on the long edge
- Under ~300KB

Check and, if needed, downsize before copying in (macOS, no extra tooling):

```bash
sips -g pixelWidth -g pixelHeight -g formatOptions "<file>"
sips -Z 1440 -s formatOptions 70 "<file>" --out apps/web/public/images/travel/japan-01.jpg
```

Report anything you resized. Never commit a multi-megabyte original.

### C3. Wire them up

Add the paths to that country's `images` array in `apps/web/lib/data/about.ts`:

```ts
images: [
  { url: "/images/travel/japan-01.jpg", alt: "Japan" },
  { url: "/images/travel/japan-02.jpg", alt: "Japan" },
],
```

`alt` is optional in the `CountryPhoto` type; the map falls back to the country name.

### C4. If the country is new to the map

The map keeps its own `PLACES` array in `travel-map.tsx`, separate from
`visitedCountries` — it keys on **numeric** ISO 3166-1 codes to match
`countries-110m.json`, while the about data keys on **alpha-2**. A new country needs an
entry in both, and the `PLACES` entry needs `iso` (numeric), `alpha2`, `name`, `city`,
`lat`, `lng`, `years` and `note`. Miss the `PLACES` entry and the country simply won't
appear on the map; miss `alpha2` and its photos won't resolve.

Also update the hardcoded country list in the `aria-label` on the map's `<svg>`.

## Route D — GitHub projects

The projects page **is** the seed. `apps/web/lib/data/autogen/gh-projects.ts` is
generated and never hand-edited; `apps/web/lib/data/projects.ts` just re-exports it.
Membership is the `featured-project` repo topic and nothing else, and the names and
blurbs are the repo's own.

See what the topic currently picks up, without writing anything:

```bash
pnpm dataseed:dry
```

It prints the matched repos and a count of the untagged ones. Then write it:

```bash
pnpm dataseed
```

Both work from the repo root. The flags live on the script itself —
`--dry-run`, `--topic=<other>`, `--owner=<user>`, `--token=<PAT>`.

### D1. Adding or removing a project

The user tags or untags the repo on GitHub (Settings → Topics → `featured-project`),
then re-runs the seed. Nothing in this repo changes. If they ask you to do the tagging,
confirm the exact repo list with them first — it edits their GitHub repos — and then:

```bash
gh api -X PUT repos/<owner>/<repo>/topics -f names[]=featured-project -f names[]=<existing>…
```

That endpoint **replaces** the whole topic list, so read the current topics first and
pass them all back, or you will wipe them.

### D2. Known limits

- **Only repos the user owns.** The seed reads `users/<owner>/repos`, so a repo under an
  org they do not control (asgardeo, wso2) can never carry their topic and will never
  appear. Thunder, the Asgardeo JS SDK and WSO2 Identity Server came off the page for
  this reason when it went tag-driven. If the user wants them back, that needs an
  explicit allowlist in the seeder — ask before building one.
- **The blurb is the GitHub description**, emoji and backticks included. The fix is to
  edit the description on GitHub, not to patch it here.
- **Forks carry their source.** The list endpoint says `fork: true` but not what it
  forked from, so the seeder spends one extra call per fork on `repos/{full_name}` and
  stores `upstream` (the chain's root, not the immediate parent). The projects row
  renders it as a "Forked from owner/repo" link, which is why `IndexRow`'s own link is
  an overlay rather than a wrapper — an anchor inside an anchor would never fire.
- Unauthenticated calls are rate-limited to 60/hour and the account has 200+ repos, so
  each run costs 3 requests. If it fails on rate limits, re-run with
  `--token=<PAT>`. Ask the user for the token; never read one out of their shell
  history, env files or config.

## Step F — Finish

Run only the checks that match what changed.

```bash
cd apps/web && npx tsc --noEmit -p tsconfig.json
cd apps/web && npx eslint app components lib
npx prettier --check <each file you touched>
```

Then look at it. Start the dev server with `preview_start {name: "web"}` (config is in
`.claude/launch.json`) and check the affected page:

- Route A → `/blog`, plus one changed post at `/blog/<slug>`
- Routes B, C → `/about`; for C, hover a map dot to confirm the thumbnails render
- Route D → `/projects`

Do not ask the user to check it manually — verify, then show them.

Finally, summarise what changed as counts and names, not a wall of diff: how many posts
were added or modified, which Instagram posts changed, which photos were added and
whether any were resized. Mention anything you deliberately left alone — a skipped reply
file, a reverted churn-only post — so it doesn't look like an oversight.

Leave committing to the user unless they asked for it.
